# Búnker Burger

Carta, carrito y checkout para Búnker Burger, Aguilares (Tucumán). La operación diaria se confirma por WhatsApp; Mercado Pago Checkout Pro es opcional.

## Desarrollo

1. Instalar Node.js 22 (`.nvmrc`).
2. Copiar `.env.example` a `.env.local` y completar las claves disponibles.
3. Habilitar pnpm con `corepack enable` (usa la versión fijada en `packageManager`) y ejecutar `pnpm install --frozen-lockfile`.
4. Enlazar la CLI con el proyecto Supabase cloud de desarrollo mediante `pnpm exec supabase link --project-ref <ref>`.
5. Revisar migraciones con `pnpm run db:push:dry` y aplicarlas con `pnpm run db:push`.
6. Ejecutar `pnpm run dev`.

Mercado Pago se ofrece solo si un checkout puede iniciarse (`getMercadoPagoAvailability`): Access Token, secreto de webhooks (`MERCADO_PAGO_WEBHOOK_SECRET`), `APP_URL` http(s) válida, método habilitado por el local, `SUPABASE_SERVICE_ROLE_KEY` y, en producción, el servicio de cuota distribuida (`RATE_LIMIT_UPSTREAM_URL`). Si falta algo se oculta y su API responde 503. Ese servicio de cuota es una dependencia operacional que todavía no está desplegada. Las claves secretas nunca llevan prefijo `NEXT_PUBLIC_`. Los pagos se acreditan sólo con lo que devuelve la API de Mercado Pago: el webhook firmado (`/api/payments/mercado-pago/webhook`) y el regreso del cliente aplican el pago con la misma regla atómica de la base; contacto mínimo y estado se guardan 90 días (ver `docs/runbooks/mercado-pago-webhook.md`).

El CI de PR ejecuta lint, typecheck, unitarios, build y Playwright; NO carga secretos ni ejecuta SQL de PR contra la base cloud. La evidencia cloud (pgTAP, Auth) no es un gate automático sino una condición de merge **por alcance**: el job informativo "Alcance de evidencia cloud" indica qué exige cada PR según los paths que cambia (migraciones, tests de base, Auth, sesiones o guardias admin), y el protocolo de `docs/runbooks/cloud-evidence.md` define cómo producirla sobre el SHA exacto, dónde registrarla y qué hacer si no se puede producir.

## Supabase y acceso a datos

- **Infraestructura actual:** existe un único proyecto Supabase cloud, identificado hoy como development, que también está previsto para producción. La separación en dos proyectos sigue pendiente (BB-19); hasta entonces no se considera un destino aislado para probar migraciones. `SUPABASE_PROJECT_ENV` es sólo una etiqueta: nunca enviar secretos a CI de PR/previews.
- **Verificación cloud confiable:** el workflow `.github/workflows/cloud-db-reviewed.yml` existe únicamente en `main` y se activa manualmente mediante `workflow_dispatch` desde la rama `main`. Solicita número de PR abierta hacia main y **SHA completo (40 caracteres) previamente revisado**. Valida mediante GitHub API que la PR y su HEAD coincidan exactamente con ese SHA y, en otro job, usa exclusivamente código/herramientas de `main`; solo extrae archivos `.sql` regulares del commit autorizado, sin instalar ni ejecutar scripts de pnpm/JS de la PR. El secreto PostgreSQL se introduce únicamente en los pasos SQL privilegiados. Si un commit cambia, exige nueva ejecución; el resultado pgTAP real publica el estado `cloud/pgTAP-reviewed` para ese SHA.
- **Acción del mantenedor para verificar antes de merge:** ir a **Actions → Cloud DB — ejecución revisada (main) → Run workflow**; seleccionar `main`, informar `pr_number`, `reviewed_sha` completo y `operation=pgTAP`. El run publica `cloud/pgTAP-reviewed` en ese SHA; se verifica con `CONTEXTS=cloud/pgTAP-reviewed node scripts/ci/verify-cloud-statuses.mjs` y se registra en un comentario de la PR (`docs/runbooks/cloud-evidence.md`). Un SHA nuevo invalida el resultado anterior. No es suficiente que un control ejecutado dentro de la PR se autodeclare autorizado.
- **Auth real revisado:** `.github/workflows/admin-auth-reviewed.yml` sólo se dispara manualmente desde `main`, valida PR/SHA exactos, exige el Environment `main` y ejecuta únicamente `scripts/check-admin-auth-cloud.mjs`, versionado en `main`. Ese harness es evidencia de configuración cloud (rechazo de contraseña inválida, owner activo de `bunker-burger` y logout local HTTP 204); **no es evidencia E2E ni ejecuta el código de la PR**. Nunca hace checkout ni ejecuta JavaScript del SHA de la PR con secretos; no sube artefactos ni reportes. Al pasar registra `cloud/admin-auth-reviewed` sobre el SHA exacto. Las pruebas de Auth del producto (`pnpm run test:integration:auth` 2/2 y `pnpm run test:e2e:admin-auth` 3/3 con `SUPABASE_TEST_REQUIRE_CLOUD=1`) ejecutan código de la PR con secretos: sólo valen corridas por `.github/workflows/admin-auth-product-reviewed.yml`, con el entorno protegido `admin-auth-product` y aprobación tras inspeccionar el SHA. Ese entorno hoy no existe, así que esa evidencia se registra como bloqueo con decisión del mantenedor (`docs/runbooks/cloud-evidence.md`).
- **Migraciones:** pgTAP corre sobre el esquema **ya aplicado** y el dry-run no ejecuta SQL, así que ninguno de los dos valida una migración nueva. Antes del merge se exige inspección del delta SQL, dry-run del SHA y, sin destino aislado, registrar el efecto como **NO verificado** con decisión del mantenedor (`docs/runbooks/cloud-evidence.md` §2.1).
- **Migraciones privilegiadas:** el mismo workflow de `main` admite `operation=dry-run` o `apply`; aplicar exige escribir exactamente `zokkgocmcaqcujltfkjf` en `confirm_project`. Nunca se aplican migraciones automáticamente desde la PR y no se debe usar `migration repair reverted` para ocultar diferencias entre ramas. El SQL proviene exclusivamente de un SHA aprobado de la PR y no se ejecutan otros archivos de esa rama.
- **Configuración administrativa imprescindible:** `SUPABASE_DEV_DB_URL` debe existir SOLO como secreto del Environment `main`, nunca como Repository/Organization secret accesible por PR. **En GitHub → Settings → Environments → main → Deployment branches, autorizar únicamente `main`; eliminar `feat/bb-05-option-engine`, `pull/27/merge` y todas las refs de PR.** Sin esa configuración fuera del repositorio no se puede demostrar el aislamiento del secreto. Comprobar disponibilidad efectiva de Environment secrets según el plan GitHub; no asumir reglas de aprobación que el plan no incluya. Si no están disponibles en repo privado, migrar el secreto a un mecanismo privilegiado realmente aislado antes de habilitar el flujo cloud; no moverlo a Repository secrets.
- **Lecturas administrativas autenticadas.** `getAdminCatalog()` valida primero la sesión con Supabase Auth (`auth.getUser()`, que detecta sesiones expiradas o revocadas) y una membresía activa en `admin_memberships` para esa tienda (`admin-access.ts`). Sin sesión, con sesión expirada, sin membresía activa o con membresía de otra tienda devuelve `unauthorized` sin leer el catálogo; nunca devuelve el subconjunto público como si fuera admin. RLS sigue siendo la barrera autoritativa.
- **La UI no habla con Supabase.** Rutas y componentes reciben objetos de dominio desde `@/server/catalog` (`getPublicCatalog`, `getAdminCatalog`). `src/test/data-access-boundary.test.ts` falla si `src/app` o `src/components` importan `@supabase/*`, los clientes, los tipos generados o consultan tablas.
- **Capas** (`src/server/catalog`): `rows.ts` (selects de PostgREST y validación con zod; el dinero viaja como texto y se convierte a `bigint`), `adapters.ts` (filas → dominio, con orden determinístico), `supabase-catalog-repository.ts` (implementa el puerto `CatalogRepository`), `catalog-service.ts` (`loadPublicCatalog` filtra categorías visibles y promociones vigentes al momento; `loadAdminCatalog` exige el gate de admin). Los grupos de opciones conservan `selectionMode` (`single`/`multiple`) tal como está persistido. Los tests unitarios inyectan `in-memory-catalog-repository.ts` e `in-memory-admin-access.ts`; no simulan una conexión a Supabase.
- **Errores controlados.** Toda lectura devuelve `Result<…, CatalogError>` con `not_found`, `unauthorized`, `unavailable`, `invalid_data` o `misconfigured`, y se registra en el log con `reportCatalogError`. Nunca se devuelve un catálogo parcial.
- **Caché.** Las lecturas públicas usan un cliente anónimo sin cookies y la caché de datos de Next (`force-cache`, 300 s, tag `catalog`). Las de administración usan la sesión del usuario (cookies) y `no-store`. La administración del catálogo invalida el tag `CATALOG_CACHE_TAG` en cada escritura (ver "Administración del catálogo"). El estado del local es la excepción: se lee siempre sin caché (ver "Estado del local").
- **Tipos generados.** `src/server/supabase/database.types.ts` sale del proyecto de desarrollo con `pnpm run db:types`, que usa `SUPABASE_DEV_DB_URL` (necesita Docker) o `SUPABASE_DEV_PROJECT_REF` (necesita `pnpm exec supabase login` o `SUPABASE_ACCESS_TOKEN`). Regenerarlo después de cada migración y commitearlo; `pnpm run db:types:check` detecta si quedó desactualizado.
- **Catálogo semilla.** `supabase/seed.sql` es idempotente (upsert por id) y solo para el proyecto de desarrollo: 4 categorías, 9 productos (1 borrador, 2 agotados, bebidas sin alcohol), grupos de opciones con defaults (incluye una opción sin stock) y 2 promociones (una activa los martes, otra pausada), con horarios de demostración en `America/Argentina/Tucuman` (lunes cerrado; viernes y sábado cruzan la medianoche) y tarifa de delivery fija. Se aplica con `pnpm exec supabase db query --linked -f supabase/seed.sql` o desde el SQL editor del proyecto de desarrollo; nunca en producción.

## Administración del catálogo

- **Pantallas.** `/bunker/admin/catalogo` tiene un tab por tipo (Hamburguesas, Sándwiches, Papas, Bebidas) con sus categorías (crear, editar nombre/slug/visibilidad, eliminar si están vacías) y productos (orden manual ↑/↓, estado publicado/borrador, stock, destacado, foto). El orden de las secciones del menú se ajusta en "Orden del menú". `/productos/nuevo` y `/productos/[id]` editan precio, stock, destacado, publicado, descripción, grupos de opciones y defaults, y foto con punto focal. No hay pedidos, facturación ni métricas.
- **Autorización.** Cada Server Action (`src/app/bunker/admin/catalogo/actions.ts`) llama a un caso de uso de `src/server/catalog-admin` que primero pasa por el mismo gate que las lecturas admin (`auth.getUser()` + `admin_memberships` activa) y toma el `store_id` de la membresía, nunca del formulario. Escribe con el cliente de sesión: RLS decide cada sentencia y una fila que RLS oculta vuelve como `not_found`. No se usa service role.
- **Publicación.** El servidor valida con `validateProductPublication` (las mismas reglas que carta y checkout): nombre, descripción, precio > 0, grupos aplicables al tipo, defaults existentes, disponibles y dentro de la cardinalidad. Un producto inválido no se publica (los borradores pueden estar incompletos, pero no tener grupos inaplicables ni defaults ajenos). Al cambiar sus grupos, un producto publicado pasa a borrador, se reemplazan los vínculos (verificando que el DELETE quitó todos los anteriores, que el INSERT guardó todos los nuevos y que la relectura da exactamente los pedidos) y recién después se publica; los triggers BB-03 vuelven a validar los defaults en la base.
- **Bebidas sin alcohol.** La app guarda siempre `contains_alcohol = false` y el trigger `products_drinks_without_alcohol` (BB-12) rechaza cualquier producto alcohólico en una categoría `drink`.
- **Fotos.** `inspectImage` (`src/server/catalog-admin/image.ts`) decide el formato por los bytes (magic numbers), no por el nombre ni el tipo declarado, y lee las dimensiones del encabezado: sólo JPEG, PNG, WebP o AVIF, hasta 5 MB y entre 320 y 4096 px por lado. Recién entonces la decodifica completa con libvips (`sharp`, warnings como error): un archivo sin datos de imagen, truncado o con datos dañados se rechaza, y el formato y tamaño decodificados deben coincidir con el encabezado. SVG, GIF, animadas y renombrados también se rechazan. Límite conocido: JPEG y WebP lossy no tienen checksum, así que unos pocos bytes alterados que igual decodifican no se distinguen de una foto real. El objeto se guarda como `<store_id>/<product_id>-<uuid>.<ext>` sin sobrescribir. Un reemplazo sube el archivo nuevo, apunta la fila y recién después borra el viejo; un borrado quita la fila antes que el archivo. `serverActions.bodySizeLimit` es `6mb` para admitir 5 MB más el overhead multipart.
- **Orden y punto focal.** La migración `20261010150000_bb12_catalog_admin.sql` agrega `products.sort_order` (orden manual dentro de la categoría; desempata destacado y nombre) y `product_images.focal_x/focal_y` (0–100, centrado por defecto), que el menú aplica como `object-position`. **El código lee estas columnas: la migración tiene que estar aplicada antes de desplegarlo** (ver `docs/runbooks/cloud-evidence.md` §2.1).
- **Caché.** Cada escritura exitosa llama `updateTag(CATALOG_CACHE_TAG)`, así el menú público lee el cambio en la próxima request. En tienda y promociones también la llama una escritura que falló después de enviarse (`mayHaveWritten`); no la llaman una validación o un permiso que frenan antes de escribir.

## Administración de tienda y promociones

- **Pantallas.** El layout admin tiene navegación Catálogo / Tienda / Promociones / Ver menú. La carta pública (`/`) es la misma con sesión admin, y suma la pestaña Admin.
- **Tienda (`/bunker/admin/tienda`).**
  - Estado calculado por el servidor (`evaluateStoreStatus`), con cierre del turno o próximo turno.
  - Override `auto`/`open`/`paused`/`closed`: `auto` y `open` exigen tarifa de delivery, en el caso de uso y en el check `stores_delivery_fee_required_to_accept_orders`. Mientras el local toma pedidos, la tarifa no se puede quitar.
  - WhatsApp normalizado a E.164.
  - Turnos semanales: se rechazan los solapados (`findOverlappingShift`), incluidos los que cruzan medianoche o la semana.
  - Medios de pago: sólo habilitación y orden. Ningún medio tiene texto configurable, porque la fila de un medio habilitado la lee cualquiera y una transferencia nunca publica alias ni datos bancarios (se piden por WhatsApp, BB-10). El nombre es fijo por medio (`PAYMENT_METHOD_NAME`) y `public_instructions` siempre está vacía; lo impone el check `store_payment_methods_fixed_public_copy` (migración `20261010220000`, que además normaliza las filas existentes). El catálogo público ni siquiera lee esas dos columnas.
  - "Lo que ve el cliente": la misma frase de estado que el storefront, la tarifa, el WhatsApp y los medios que ofrece el checkout, con su mismo texto (`src/domain/public-payment-options.ts`): Mercado Pago sólo si está disponible ahora, sin cambiar la preferencia guardada.
- **Promociones (`/bunker/admin/promociones`).**
  - Listado en el orden en que se prueban (mayor prioridad primero), con fase: en vigencia, fuera de franja, programada, vencida o pausada.
  - Pausar y reanudar.
  - Reordenar: `admin_move_promotion` intercambia prioridades con la vecina en una sola transacción (pasando por un valor libre, porque `(store_id, priority)` es único); nadie ve el estado intermedio y un fallo no deja nada a medias.
  - Alta, edición y baja con productos, canales, fechas en la zona del local y franjas semanales. `admin_save_promotion` guarda la fila, sus productos y sus franjas en una sola transacción: o queda todo o nada, y una promoción activa no se pausa al editarla.
  - Las dos funciones son `SECURITY INVOKER` (RLS decide cada fila), exigen que la sesión administre la tienda (`catalog_rls.is_store_admin`) y toman un lock por tienda, así dos admins no calculan la misma prioridad. Sólo `authenticated` puede ejecutarlas.
  - La vista previa calcula los precios derivados con `promotionDiscount`, el mismo motor del checkout. Hay tests que comparan su resultado con `quoteCart`.
- **Secretos.** Las pantallas y respuestas admin nunca leen ni devuelven credenciales. De Mercado Pago solo llega si está disponible y por qué no (motivos como "falta configurarlo en el servidor"), nunca su configuración. Lo cubren los tests de página y el e2e admin-auth, que busca los valores reales del entorno en el HTML.
- **Código compartido.**
  - `src/server/admin/use-case.ts`: gate, `store_id` de la membresía, mensajes y log.
  - `src/server/admin/supabase-writes.ts`: escrituras con filas afectadas y mapeo de errores.

  Los usan catálogo, tienda y promociones, y cada escritura invalida `CATALOG_CACHE_TAG`. No hay migraciones: BB-08 y BB-09 ya crearon el esquema y las policies.

## Estado del local, horarios y delivery

- **Fuente de verdad en la base.** `stores.status_override` es el switch manual: `auto` (sigue los horarios), `open`, `paused` o `closed`; una tienda nueva arranca `closed`. `store_business_hours` guarda tramos semanales en la zona horaria de la tienda (`America/Argentina/Tucuman` por defecto, validada por trigger): `day_of_week` es el día en que abre el tramo y un `closes_at` que no es posterior a `opens_at` cierra al día siguiente (`00:00` = a medianoche). `stores.is_open` y `stores.business_hours` quedan deprecadas y la app no las lee.
- **Tarifa obligatoria.** `delivery_fee_cents` es `null` hasta configurarla y la base rechaza `auto`/`open` sin tarifa; el dominio, además, nunca acepta pedidos sin ella. No hay barrios, radios, mapas ni zonas: la tarifa es fija.
- **Decisión server-side, siempre fresca.** `evaluateStoreStatus` (`src/domain/store-status.ts`) calcula estado, `acceptingOrders`, cierre del tramo actual y próxima apertura con instantes reales de la zona horaria (correcto ante cambios de horario y cruces de medianoche; tramos contiguos se unen). `getStoreStatus()` (`@/server/catalog`) lee override, zona, tarifa y horarios con su propio select y el cliente operativo `createOperationalReadClient` (`cache: "no-store"`), separado de la lectura cacheable del catálogo: una pausa, un cierre o un cambio de tarifa rigen en la siguiente consulta, cotización o pago sin depender de invalidar `CATALOG_CACHE_TAG`. El service worker sirve `/api/store/status` solo desde la red (NetworkOnly).
- **Endpoint público.** `GET /api/store/status` devuelve el estado mínimo (`state`, `acceptingOrders`, `reason`, `closesAt`, `nextOpeningAt`, `deliveryFeeCents` como texto, `timezone`) con `Cache-Control: no-store`; ante cualquier error responde 404/503 con `acceptingOrders: false`.
- **Cerrado bloquea pagar y enviar, no navegar.** La carta y el carrito nunca consultan el estado. El checkout lo pide a `/api/store/status` solo para explicarlo (cerrado, pausado, próxima apertura) y mostrar la tarifa del servidor; ante un error dice que no pudo verificarlo. La web no ofrece ninguna acción de envío: hasta que BB-10 genere el mensaje desde una cotización validada en el servidor, el botón de WhatsApp queda deshabilitado (un total calculado en el navegador nunca confirma un pedido). `createAuthoritativeQuote` exige un local abierto y toma la tarifa únicamente del estado (una vez por pedido, nunca en retiro); `createCheckoutProPreference` lo vuelve a verificar antes de crear el pago en Mercado Pago.

## Promociones

- **Un solo motor** (`src/domain/promotions.ts`), usado por la cotización del servidor y por la estimación del navegador. Una regla está vigente si está activa (no pausada), `starts_at <= ahora < ends_at` y, si tiene `promotion_schedule`, la hora local de la tienda cae en uno de sus tramos semanales. Si `ends_at` es anterior a `starts_at`, el tramo cruza la medianoche (22:00–02:00); si son iguales, el tramo está vacío y nunca activa la regla.
- **No acumulables.** A cada pedido se aplica como máximo una promoción: entre las vigentes que le dan descuento gana el `priority` más alto, con desempate estable por `id`. No hay cupos, contadores ni topes por unidades.
- **Mecánicas** (`promotion_items` define los productos alcanzados):
  - `percent_off`: porcentaje de lo que se paga por esos productos (o por todo el pedido si no lista ninguno). Se calcula exacto en puntos básicos y se redondea hacia abajo.
  - `fixed_price`: combo. Cada set completo de productos × cantidad cuesta el precio fijo en lugar de sus precios base; los extras de opciones se cobran igual.
  - `buy_x_get_y`: por cada `buy + get` unidades, las `get` más baratas (a precio base) son gratis.
  - `free_delivery`: anula la tarifa de envío una sola vez, solo en delivery.
- **Cotización autoritativa.** `createAuthoritativeQuote` recibe las reglas de `PricingRepository.listPromotions()` y guarda la promoción aplicada en el snapshot (`PaymentQuote.promotion`), que reutilizan el mensaje de WhatsApp y Mercado Pago. `getPromotionsForQuote()` (`@/server/catalog`) lee las reglas con el cliente operativo sin caché, así una pausa rige en la próxima cotización. El navegador no envía precios, descuentos ni ids de promoción: el schema de checkout los rechaza.
- **Fuente pública real.** La carta y el total estimado leen `GET /api/store/promotions`: las mismas reglas que `getPromotionsForQuote()`, sin caché (`no-store`, y el service worker nunca la guarda), sin `description` ni `badge_text`, con los productos identificados por slug. El navegador la vuelve a leer cada minuto y al volver a la pestaña, así una pausa o un cambio de porcentaje llega a la página abierta. Si el endpoint falla, no se anuncia ningún descuento; no existe copia estática de reglas.
- **UI sin texto de precio libre.** El precio tachado sale del precio real y es exactamente lo que `quoteCart` descontaría a ese producto solo con la modalidad elegida (`promotionalPrice`): una promoción solo delivery no se anuncia mientras está elegido retiro, y si la que ganaría es envío gratis no se tacha nada. La explicación se genera desde la mecánica (`explainPromotion`); nunca se muestran `description` ni `badge_text` como precio.

## PWA, instalación y caché

- **Instalable.** `src/app/manifest.ts` (inicio y alcance `/`, standalone, `theme_color` = `--color-canvas`) con íconos provisionales 192/512, uno maskable y `apple-touch-icon` (`public/icons`, generados con `node scripts/generate-pwa-icons.mjs`). El e2e `tests/e2e/pwa.spec.ts` comprueba con la API de instalabilidad de Chrome (`Page.getInstallabilityErrors`) que no haya errores.
- **Política de caché** (`src/app/sw-routes.ts`, con tests unitarios; `src/app/sw.ts` sólo la aplica). Lo que no está listado va a la red:
  - **NetworkOnly:** `/bunker/**` (login y Admin), toda `/api/**` (checkout, estado, promociones, catálogo fresco), payloads RSC, Server Actions, cualquier método que no sea GET y el regreso de Mercado Pago (`/?ref=…`).
  - **NetworkFirst:** el documento de la carta (`/`, también con `?producto=`), con 4 s de espera antes de usar la copia. Sólo se guarda HTML 200 same-origin sin redirección. Como el primer documento llega antes de que exista el worker, al activarse el worker pide `/` sin credenciales y guarda esa copia anónima: la primera visita ya abre offline, sin recargar.
  - **StaleWhileRevalidate:** imágenes (`/_next/image`, íconos) y las fotos del bucket público `catalog` del proyecto Supabase del build (`NEXT_PUBLIC_SUPABASE_URL`). Esas fotos se piden con CORS y sin credenciales; nunca se guarda una respuesta opaca, Auth, PostgREST, URLs firmadas ni otros buckets. Máximo 120 imágenes, 30 días. **CacheFirst:** `/_next/static` (con hash).
  - **Offline:** un documento que no se puede traer ni está en caché muestra `/offline`, precacheada en cada build y sin datos.
- **Offline nunca se envía ni se paga.** La carta y el carrito siguen funcionando con lo cacheado. El checkout oculta el link de WhatsApp y deshabilita Mercado Pago mientras `navigator.onLine` es `false` (`useOnlineStatus`).
- **Actualización segura.** El worker nuevo espera (`skipWaiting: false`). La página ofrece "Actualizar"; al aceptar recibe `SKIP_WAITING` y la página se recarga. Si otra pestaña actualizó, ofrece "Recargar". Al activarse borra los documentos cacheados de la versión anterior y las cachés de workers viejos, así un shell viejo nunca corre contra assets nuevos. `/sw.js` se sirve con `Cache-Control: no-cache, no-store` y una CSP cuyo `connect-src` sólo admite el propio origen y el de Supabase del build.
- **E2E de fotos** (`tests/e2e/pwa-photos.spec.ts`): necesita un build con `NEXT_PUBLIC_SUPABASE_URL`. Apunta ese host a un Storage HTTPS local con certificado efímero (requiere `openssl`), porque Playwright no enruta los pedidos cross-origin de un service worker. CI usa el placeholder `https://e2epwafixture0000001.supabase.co`.
- **Cerrar sesión purga** la copia de la carta, que pudo quedar con la pestaña Admin, y cualquier entrada bajo `/bunker` o `/api` (`purgeSessionCaches`). Admin nunca se cachea.
- **Aviso de instalación discreto:** sólo después de agregar un producto en esa visita, nunca si ya está instalada, y no vuelve por 30 días si se descarta. En iOS, que no tiene diálogo de instalación, muestra los pasos de Safari (Compartir → "Agregar a inicio").

## UI

Tailwind CSS 4.3 se carga desde `src/app/globals.css`, que es la única fuente de tokens (colores, tipografía, radios, sombras, `tap` de 44 px y ancho `content` de 1280 px). La paleta por defecto de Tailwind está deshabilitada: usar solo utilidades de tokens (`bg-surface`, `text-primary`, `text-headline-md`, `rounded-lg`, `min-h-tap`…) o `var(--color-*)` en CSS. Oswald (títulos y precios) y Space Grotesk (cuerpo y controles) se cargan con `next/font`.

- Primitives en `src/components/ui`: Button, Card, Badge, Dialog, Drawer, Tabs, Input, Textarea, Select, Switch, Label, Skeleton, EmptyState/ErrorState y Toaster (`toast` de sonner).
- Shell en `src/components/shell`: `AppShell`, `SiteHeader`, `Container` y la única `BottomNav`, que respeta safe areas y se oculta mientras el teclado virtual está abierto.
- `/design-system` muestra todos los primitives y estados; se sirve en local y previews, nunca en producción (`VERCEL_ENV=production`). Playwright la audita con axe (WCAG 2.1 AA), teclado y targets de 44 px, y `tests/e2e/responsive.spec.ts` recorre carta y demo a 320, 390, 768 y 1280 px.
- `src/test/design-tokens.test.ts` falla si aparecen colores, familias, tamaños, tracking o radios hardcodeados fuera de `globals.css` (la geometría de layout queda fuera a propósito).
- shadcn/ui está configurado en `components.json`. Al agregar componentes con `pnpm dlx shadcn@latest add <componente>`, adaptarlos a los tokens; si se suman tokens nuevos, registrarlos también en `src/lib/utils.ts` para que `cn` los combine bien.

## Excepciones de versiones

Todas las dependencias directas están fijadas a versiones exactas y el lockfile está versionado.

- **TypeScript 6.0.3** en lugar de 7.x: `typescript-eslint` (usado por `eslint-config-next`) solo soporta `>=4.8.4 <6.1.0` y aborta con TS 7. Volver a `latest` cuando typescript-eslint publique soporte (ver typescript-eslint/typescript-eslint#10940).
- **Build con webpack** (`next build --webpack`): `@serwist/next` todavía no soporta Turbopack. El desarrollo sigue usando Turbopack con el service worker desactivado.
